專題緣起與核心突破
Project Vision

打破傳統 Chatbot 三大高昂門檻

解決伺服器維護費、API 免費配額遭刷爆、以及缺乏記錄稽核之痛點

痛點 1：主機成本高
傳統 Node/Python 需要每月租用 VPS 或本地常駐開機，維護成本居高不下。

👉 解法：採用 Google Apps Script 官方免費託管，24/7 永不休眠且零主機費。
痛點 2：配額遭盜刷
公開 Webhook 暴露在外，任何路人傳訊息皆會瞬間抽乾 Gemini 免費額度。

👉 解法：雙重安全鎖（白名單 ID 驗證 + 每日請求計數器），未授權者即刻阻擋。
痛點 3：紀錄散落無稽核
問答過程無系統化留存，無法統計 Token 成本與對話內容。

👉 解法：Container-Bound 試算表即時記錄時間戳、用戶 ID、Prompt 與 Tokens。

系統架構與技術棧
System Architecture

高可用無伺服器 (Serverless) 資料流

在 Google Cloud 全球骨幹網路上完成請求認證、短時快取與 LLM 推理

端到端資料流水線
1. 用戶發送訊息：Telegram / LINE Bot 送達 GAS Webhook。
2. 入口層去重 & 防重擊：快取 Update ID，立即響應 200 OK 阻絕重發風暴。
3. 身分與配額攔截：比對 ALLOWED_USER_IDS 與當日使用量。
4. 短期記憶組裝：自 CacheService 撈取最近 4 輪歷史對話。
5. Gemini 2.5 推論：注入真實系統時間，支援 429 搜尋額度自動無感降級。
6. 試算表記錄：非同步寫入 Google Sheets 完整稽核日誌。
核心模組分工矩陣
• Main.gs：Webhook 路由、Update ID 快取、指令解析。
• Gemini.gs：REST 通訊、8192 Token、429 降級、時鐘注入。
• Telegram.gs：長文分段、Markdown 轉 HTML、標籤自動修復。
• QuotaManager.gs：白名單過濾、每日限額跨日重置。
• Storage.gs：對話記憶序列化、Google Sheets 自動記錄。

AI 協作開發與避坑精要
Troubleshooting & Lessons Learned

實務開發避坑經驗總結

記錄開發過程中踩坑與迅速排錯的工程思維

避坑 1：Telegram 訊息無限迴圈
現象： 測試時 Telegram 不斷跳出重複回覆。
原因： GAS 外部 API 耗時超過 Telegram 預期，伺服器判定未送達而觸發重發機制。
對策： 在 `Main.gs` 入口利用 `CacheService` 鎖定 `update_id`，5 分鐘內同 ID 直接忽略，成功平息重發風暴。
避坑 2：Search Grounding 429 配額陷阱
現象： 開啟聯網搜尋後，Telegram 頻繁收到 HTTP 429 錯誤。
原因： Google AI Studio 免費帳號中，Google Search Grounding 的預設配額為 0。
對策： 於 `Gemini.gs` 實裝 429 偵測無感降級，背景自動拔除 tools 並以基準模型回答，永遠不向用戶報錯。
